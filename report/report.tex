% ===================== ABSTRACT =====================
\noindent\textbf{Abstract.}~%
We present our highly performant columnar store query engine.
It implements \textbf{15 distinct optimisations}, spanning five architectural layers.
They include encoding (Dictionary, Precomputed aggregates, RLE town compression), Physical layout (Pre-sorted clustering, Per-column binary files, Town partitioning), Indexing (Zone maps, Bitmap indices, Binary search), Scan-path rewriting (Result reuse, Late materialisation, Predicate reordering, Integer gating), and I/O management (Chunked streaming, Memory-mapped I/O).
All optimisations are toggleable by boolean flags.
This enables us to build a combinatorial evaluation suite testing across 40 permutations of optimisations, each with correctness verification.
Physical town partitioning together with Result reuse achieves a \textbf{3,389$\times$ query speedup} at only 660\,KB memory.
Memory-mapped I/O with Result Reuse has the fastest end to end time of \textbf{71.9\,ms}, 67.3$\times$ faster than baseline.
Negative results are instructive as well.
Bitmap indexing ($0.15\times$) and Predicate reordering ($0.06\times$) show that remove cheap predicates via an expensive process greatly affects performance, especially when data is already well filtered upstream.

\subsection{Encoding and Layout Decisions}\label{sec:layout-discussion}

\paragraph{Dictionary Encoding.}
Our \texttt{DictionaryEncoder} is a bidirectional \texttt{unordered\_map}/\texttt{vector} pair that maps each of the unique 26 towns to a \texttt{uint16\_t} ID.
During queries, our engine would first resolve the target town list to IDs once outside the scan, before checking for integer equality in the inner loop.
This brought about a 32\% query speedup (2,299$\to$1,573\,ms) at the cost of +2.9\% memory and 16.7\% slower load time.
The increased load time is a one-time penalty amortised across all the queries.

\paragraph{Column Splitting of \texttt{Month}.}
We split the date string into two integer columns at parse time.
This eliminates repeated string parsings and allow for direct \texttt{uint16} range predicates.
Using just the Year predicate alone eliminates ${\sim}90\%$ of rows.

\paragraph{Precomputed PricePerSqm.}
The storing of \texttt{(price / area)} as \texttt{float32} will reduce the per-row floating point division we had to do for entries that survived the filter.
Only ${\sim}0.2\%$ of row iterations reach this division, the ${\sim}543$ survivors per query.
This is why the measured speed up is only $<$0.1\%.

\paragraph{Pre-sorted Clustering.} \label{para:pre_sorted_clustering}
A \texttt{stable\_sort} by the key (Town, Year, Month) will physically reorder all columns once at ingestion.
A linear pass then records each town partition's \texttt{[begin, end)} boundaries at a $O(1)$ lookup cost at query time.
This is a building block for binary search (\S\ref{sec:binsearch}) and zone map chunking (\S\ref{sec:zonemaps}).

\paragraph{Separate Binary Column Files.} \label{para:separate_binary_files}
Every column is written to its own binary file during the CSV to columnar database conversion.
During query time, only the five filtered columns are loaded.
Output columns are lazy loaded for each surviving row per $(x,y)$ pair.
The value of this optimisation is in memory and load-time reduction; memory usage drops by 96.2\% from 71.4\,MB to 2.7\,MB, while load time also significantly falls from 2,536\,ms to 68\,ms. However, it incurs a 2.0\% \emph{slowdown} in query time, because the binary I/O path still performs a full scan.

\subsection{Zone Maps}\label{sec:zonemaps}
Every numeric filter column is divided into fixed size chunks of 1,024 rows, each storing a \texttt{(min, max)} entry.
Hence, there will be 254 chunks in total, with a size of $<$8\,KB.
With \S\ref{para:pre_sorted_clustering}, a significant 96.1\% of chunks are skipped across all 568 queries (138.6K of 144.3K chunks skipped), proving its time efficiency.

\subsection{Bitmap Index on Town}\label{sec:bitmap}
We build one \texttt{std::vector<bool>} for each distinct town at load time (26 bit-vectors $\times$ 259K bits $\approx$ 842\,KB).
Before querying, bit vectors for the specific towns are OR combined into a \texttt{uint8\_t}-per-row mask ($\sim$259\,KB).
This replaces the per-row town predicate with a single array lookup.
The mask uses one byte per row for cache line friendly sequential access.
As explored in \S\ref{sec:negative}, this optimisation hurts performance.
Eliminating all 12.55M Town comparisons yielded just $0.15\times$ throughput.
Its overhead outweighted the cost of original comparisions as the Year predicate already filters out ${\sim}90\%$ of rows before Town is reached.

\subsection{I/O Layer: Chunked and Memory-Mapped }\label{sec:io}

\paragraph{Chunked I/O.}
Our system streams filtered columns from \S\ref{para:separate_binary_files} in bounded size chunks under a configurable memory budget.
The outer loop iterates over the I/O chunks, while the inner loop runs all 568 queries per chunk.
It exploits the associativity of \texttt{min} to merge per-chunk winners.

\paragraph{Memory-mapped I/O.}
This feature replaces \texttt{ifstream}/\texttt{fread} with POSIX \texttt{mmap(2)}.
It means each \texttt{.col} file is mapped into virtual address space with a single syscall, then \texttt{memcpy}'d into the existing column vectors.
Load times drop from 68\,ms (A9 \texttt{ifstream}) to 31\,ms , a 55\% reduction.
For lazy materialisation, \texttt{loadStringAtMmap} replaces \texttt{std::ifstream} construction with raw POSIX calls.
Combined with \S\ref{sec:reuse}, it achieves the fastest total time of \textbf{71.9\,ms} (67.3$\times$ end-to-end).

\subsection{Physical Partitioning by Town}\label{sec:partition}
Columnar binary files are split into one subdirectory per town.
This is how we implemented partition pruning.
During a query, \texttt{loadColumnFilesPartitioned} opens only the subdirectories for the target town and concatenates their columns into the in-memory \texttt{ColumnStore}:

\begin{lstlisting}[caption={Simplified code for partition loading.}]
void loadColumnFilesPartitioned(const string& base_dir,
        const vector<string>& target_towns, ColumnStore& db) {
    for (const auto& town : target_towns) {
        string dir = base_dir + "/" + town;
        // append filter + materialisation columns from dir
        appendNumericCol(db.col_month_year, dir+"/month_year.col");
        appendNumericCol(db.col_floor_area, dir+"/floor_area.col");
        // ... remaining columns ...
    }
    // rebuild zone maps / bitmap indices over concatenated data
}
\end{lstlisting}

For 3 target towns, only 42,935 of 259,237 rows are loaded, a 83.4\% reduction.
If a row is in memory, it implicitly means that it must belong to a target town.
No other town comparisions are then needed.
Memory footprint also drops to \textbf{660\,KB}, which is 99.1\% less than baseline.

\subsection{RLE on Sorted Towns}\label{sec:rle}
We implement run-length encoding on sorted town columns by compressing \texttt{town\_encoded.col} into (value, start, length) triples:
\[
  \texttt{run\_value}[k],\; \texttt{run\_start}[k],\; \texttt{run\_length}[k].
\]
The query engine resolves requested towns to run IDs and scans only the selected intervals, skipping non-matching runs entirely instead of checking town equality for every row.
Without pre-sorting (\S\ref{sec:layout-discussion}), the unsorted column produces 2,570 runs; the engine still skips 122.86M rows via run boundaries, reducing rows scanned post-RLE to 24.39M and achieving a 10.5$\times$ query speedup.
With pre-sorting, each town now forms a single contiguous run (26 runs total), and town comparisons drop to zero.
The strongest composition happens when including binary search techniques, which narrows each town partition to the target month range, and RLE eliminates all remaining town equality checks, yielding a 180$\times$ query speedup (13.7\,ms query time).

\subsection{Exception Handling}\label{sec:except}
In empty result sets, we return a ``No result'' row in our output.
If there are ties in minimum price-per-sqm, the system only keeps the first one it sees during scans.

% ===================== SECTION 2: DATA PROCESSING =====================
\section{Data Processing}\label{sec:processing}

\subsection{Baseline Scan}\label{sec:baseline}
The baseline scans all 259,237 rows for each of 568 $(x,y)$ pairs.
Predicates are evaluated in the order Year ~$\to$~ Month ~$\to$~ Town ~$\to$~ Area; Year is checked first because it eliminates ${\sim}90\%$ of rows with a single \texttt{uint16} equality before the more expensive Town iteration runs.

\begin{lstlisting}[caption={Baseline scan loop in \texttt{runQuery} (simplified).}]
for (size_t i = 0; i < N; ++i) {
    if (db.col_month_year[i] != target_year) continue;  // ~90% eliminated
    if (db.col_month_month[i] < start_month ||
        db.col_month_month[i] > end_month)  continue;
    // Town: linear scan over 7-element target list
    bool match = false;
    for (const auto& t : towns)
        if (db.col_town[i] == t) { match = true; break; }
    if (!match) continue;
    if (db.col_floor_area[i] < y) continue;
    double ppsm = (double)db.col_resale_price[i] / db.col_floor_area[i];
    if (ppsm < min_ppsm) { min_ppsm = ppsm; best_i = i; }
}
\end{lstlisting}

Across the full grid this produces 147.25M row iterations and 12.55M town comparisons, averaging 4,835.6\,ms total (2,536.1\,ms load + 2,299.5\,ms query).

\subsection{Composable Scan Architecture}\label{sec:compose}

All 15 optimisations are controlled by independent boolean flags in the \texttt{ColumnStore} struct (toggled via \texttt{OptConfig} in the evaluation suite).
The query engine has three paths: (1)~a \emph{reuse path} (\S\ref{sec:reuse}) that short-circuits via the cumulative table, (2)~a \emph{unified scan loop} where each flag controls one orthogonal decision; \textbf{Dictionary Encoding} selects int vs.\ string comparison, \textbf{Zone Maps} wraps the loop in chunk-level pruning, \textbf{Bitmap Indexes} replaces the town predicate with a bitmap mask, \textbf{RLE} replaces per-row town checks with run-level skipping, \textbf{Predicate Ordering} reorders predicates, \textbf{Integer Early-Exit Gates} float computation, \textbf{Precomputed PricePerSqm} selects the PPSM source, and \textbf{Late Materialization} defers the price column to a Phase~2 survivors pass, and (3)~a \emph{partition-pruned path} (\S\ref{sec:partition}) that loads only target-town data before entering either path~(1) or~(2).
\textbf{Memory-mapped I/O} is an I/O-layer substitution under \textbf{Separate Binary Column Files} , transparent to the scan logic.
This composability allows the evaluation suite to test ${\sim}40$ configurations and isolate each contribution.

\subsection{Result Reuse}\label{sec:reuse}

The 568 queries overlap: for fixed $y$, the month window for $x{=}k$ is a superset of $x{=}k{-}1$; for fixed $x$, every record with $\texttt{area} \ge y$ also satisfies $\texttt{area} \ge y{-}1$.

\paragraph{Three-step Cumulative Table Build.}
\textbf{Step~1 (single $O(N)$ scan):} For each row passing year and town filters, compute $\textit{offset} = \texttt{month} - \textit{start} + 1$ (range 1--8) and $\textit{bucket} = \min(\texttt{area},\, 150)$.
Records with $\texttt{area} > 150$ are \emph{clamped} to bucket 150, not dropped. This is correct because every valid $y$ threshold is $\le 150$, so a record with area 160 satisfies every $y$ and must contribute to all buckets it qualifies for. The clamped bucket propagates into all lower buckets during the Y-sweep.
\textbf{Step~2 (X-sweep):} For each area bucket, sweep offsets $1 \to 8$, propagating a running minimum.
\textbf{Step~3 (Y-sweep):} For each offset, sweep area $149 \to 80$, propagating the minimum downward.
After Step~3, \texttt{cum\_table[x][y]} holds the answer for each $(x,y)$ pair, and the query phase becomes a single O(1) array lookup.
The full C++ implementation is given in Figure~\ref{fig:cumtable} (Appendix).

\paragraph{Results.}
This optimisation alone reduces query time from 2,299.5\,ms to 4.6\,ms (499$\times$ query speedup), with rows scanned dropping from 147.25M to 259.2K (the single build scan).
When combined with \textbf{Dictionary Encoding}, query time drops further to 3.1\,ms (749$\times$).

\subsection{Pre-sort + Binary Search}\label{sec:binsearch}

With data pre-sorted by (Town, Year, Month), the query engine runs custom \texttt{lowerBound}/\texttt{upperBound} searches within each town partition using a linearised month key ($\texttt{year} \times 12 + \texttt{month} - 1$):

\begin{lstlisting}[caption={Binary search on linearised month key.}]
inline uint32_t monthKey(uint16_t year, uint8_t month) {
    return (uint32_t)year * 12u + (uint32_t)(month - 1u);
}
size_t lowerBoundMonthKey(const ColumnStore& db, size_t l, size_t r,
                          uint32_t key) {
    while (l < r) {
        size_t mid = l + (r - l) / 2;
        if (monthKeyAt(db, mid) < key) l = mid + 1; else r = mid;
    }
    return l;
}
\end{lstlisting}

Rows scanned drop from 147.25M to 751.7K (99.5\% reduction), town comparisons fall to zero, and query time drops to 11.9\,ms (193$\times$ query speedup).
This is an independent scan-elimination path from \textbf{Result Reuse}.

\subsection{Late Materialisation (Two Phases)}\label{sec:c3}

Phase~1 applies only the four predicate columns, appending survivor indices to a vector.
Phase~2 iterates survivors to fetch Resale\_Price, compute PricePerSqm, and track the minimum.
Measured result: 0.7\% \emph{slowdown} (2,315\,ms vs.\ 2,299\,ms), essentially within measurement noise, because the overhead of maintaining the survivor vector roughly cancels the cache savings from deferring a single 4-byte column.

\subsection{Other Scan Optimisations}\label{sec:other}

\paragraph{Zone-map Chunk Skipping (\S\ref{sec:zonemaps}).}
Before scanning a 1,024-row chunk, the engine tests its min/max against Year, Month, and Floor\_Area predicates; failing chunks are skipped entirely (96.1\% skip rate, 25\% standalone query speedup; combined with A1: 58\%).

\paragraph{Bitmap-driven Row Filtering (\S\ref{sec:bitmap}).}
A precomputed \texttt{uint8\_t} mask replaces the per-row town loop with a single byte lookup.
Town comparisons drop to zero, but query time regressed to $0.15\times$ ($15{,}670$\,ms vs.\ $2{,}299$\,ms baseline): the byte-load-plus-branch on every row is more expensive than the original integer comparison that runs only on the ${\sim}10\%$ of rows surviving the Year filter.
This confirms that the baseline Year$\to$Month$\to$Town order is already near-optimal.

\paragraph{Predicate Reordering.}
Reordering to Town~$\to$~Year~$\to$~Month~$\to$~Area caused a $0.06\times$ regression: town comparisons surged from 12.55M to 417.51M because every row now pays the expensive Town list iteration before the cheap Year check can eliminate it. The lesson: optimal order must minimise \emph{cost~$\times$~pass\_rate}, not maximise selectivity alone.

\paragraph{Integer Early-exit Gate.}
Tests $\texttt{price} \times \texttt{cur\_min\_area} \ge \texttt{cur\_min\_price} \times \texttt{area}$ in \texttt{uint64} before computing float PricePerSqm.
Measured: within noise---too few survivors (${\sim}543$/query) for the eliminated float work to register.

\subsection{Correctness Argument}\label{sec:correctness}

Each optimisation preserves output equivalence:
\textbf{Dictionary Encoding}~is a bijection.
\textbf{Pre-sorted Clustering}~is a permutation.
\textbf{Precomputed PricePerSqm}~is identical to runtime division.
\textbf{Separate Binary Column Files}~reproduce identical column vectors.
\textbf{Zone Maps}~skip a chunk only when its (min, max) proves no row can match.
\textbf{Bitmap Index on Town}~mask is the OR of exact per-town bit-vectors; the mask lookup is equivalent to the membership test it replaces.
\textbf{Binary Search}~locates exact boundaries in sorted data.
\textbf{Result Reuse}~is exact because $\min$ is associative over disjoint month ranges and monotone over area thresholds; clamping area $> 150$ to bucket~150 is correct because all valid $y \le 150$.
\textbf{Late Materialization}~defers column access without altering the predicate set.
\textbf{Predicate Ordering}~changes evaluation order, not the predicates.
\textbf{Integer Early-Exit Gate}~is a sufficient condition for ``cannot beat current minimum.''.
\textbf{Chunked I/O}~processes the same rows in bounded batches; the cumulative table is merged across chunks via the associativity of $\min$.
\textbf{Memory-mapped I/O}~\texttt{memcpy} from mapped region produces byte-identical vectors as \texttt{fread}.
\textbf{RLE on Sorted Towns}~run boundaries mark contiguous blocks of identical town values; skipping a non-matching run is equivalent to skipping each row individually.
\textbf{Physical Partitioning by Town}~partition loading concatenates disjoint town subsets; the union equals the set of rows matching the town predicate.
All ${\sim}46$ configurations produced byte-identical output, verified by the evaluation suite's per-result hash comparison (\S\ref{sec:correct-inv}).

% ===================== CONCLUSION =====================
\section{Conclusion}\label{sec:conclusion}
The largest query-time win was \textbf{Result Reuse}: a single $O(N)$ build pass replaced $568 \times O(N)$ scans with $O(1)$ lookups (499$\times$ query speedup; 749$\times$ with A1).
\textbf{Physical Town Partitioning} reduced the build-pass input from 259.2K to 42.9K rows, yielding 3{,}389$\times$ query speedup and 660\,KB memory---the most memory-efficient configuration.
The fastest end-to-end configuration was \textbf{mmap + Result Reuse} at 71.9\,ms total (67.3$\times$), where \textbf{mmap's} 55\% load-time reduction composed with reuse's scan elimination.
The most instructive failures were \textbf{Predicate Reordering} ($0.06\times$) and \textbf{Bitmap Index on Town} ($0.15\times$): \textbf{Predicate Reordering} demonstrated that optimal predicate order must minimise cost\,$\times$\,pass\_rate, while \textbf{Bitmap Index on Town} showed that eliminating a cheap predicate via a more expensive mechanism can regress performance when upstream predicates already prune effectively.
Across all 15 optimisations and ${\sim}40$ tested configurations, every result was byte-identical to the baseline; correctness was never sacrificed for speed.
If revisiting this project, we would explore a cost-based predicate optimiser that dynamically selects evaluation order.

std::vector<std::vector<MinEntry>> buildCumulativeTable(
    const ColumnStore& db, uint16_t target_year,
    uint8_t start_month, const std::vector<std::string>& towns) {
  const std::size_t N = db.size();
  std::vector<std::vector<MinEntry>> per_x(9, std::vector<MinEntry>(151));
  // Pre-resolve town IDs (dict-encoded) or build hash set (string path)
  std::unordered_set<std::string> town_set;
  std::vector<uint16_t> town_ids;
  if (db.use_dict_encoding)
    for (auto& t : towns) { uint16_t id; if (db.dict_town.lookup(t,id)) town_ids.push_back(id); }
  else town_set.insert(towns.begin(), towns.end());
 
  // --- Step 1: Single O(N) scan --- per-(offset, bucket) minimum ---
  for (std::size_t i = 0; i < N; ++i) {
    if (db.col_month_year[i] != target_year) continue;           // year filter
    const uint8_t month = db.col_month_month[i];
    if (month < start_month) continue;
    int offset = int(month) - int(start_month) + 1;
    if (offset < 1 || offset > 8) continue;                      // month range
    if (db.use_dict_encoding) {                                   // town filter
      bool match = false; uint16_t rid = db.col_town_encoded[i];
      for (auto& tid : town_ids) if (rid == tid) { match=true; break; }
      if (!match) continue;
    } else { if (town_set.find(db.col_town[i]) == town_set.end()) continue; }
    const unsigned area = db.col_floor_area[i];
    if (area < 80) continue;                                      // below all y
    const unsigned bucket = (area > 150) ? 150u : area;           // clamp
    const double ppsm = db.use_precomputed_ppsm
        ? db.col_price_per_sqm[i]
        : double(db.col_resale_price[i]) / double(db.col_floor_area[i]);
    MinEntry& e = per_x[offset][bucket];
    if (!e.has || ppsm < e.ppsm) { e.has=true; e.ppsm=ppsm; e.idx=i; }
  }

  // --- Step 2: X-sweep --- cumulative min across month offsets ---
  std::vector<std::vector<MinEntry>> cum_x(9, std::vector<MinEntry>(151));
  for (int area = 80; area <= 150; ++area) {
    MinEntry running;
    for (int off = 1; off <= 8; ++off) {
      if (per_x[off][area].has)
        if (!running.has || per_x[off][area].ppsm < running.ppsm) running = per_x[off][area];
      cum_x[off][area] = running;
    }
  }
  // --- Step 3: Y-sweep --- propagate min from higher to lower area ---
  for (int off = 1; off <= 8; ++off)
    for (int area = 149; area >= 80; --area) {
      const MinEntry& hi = cum_x[off][area+1]; MinEntry& lo = cum_x[off][area];
      if (hi.has && (!lo.has || hi.ppsm < lo.ppsm)) lo = hi;
    }
  return cum_x;  // O(1) lookup: cum_x[x][y]
}
