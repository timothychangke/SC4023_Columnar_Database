% ===================== ABSTRACT =====================
\noindent\textbf{Abstract.}~%
We present a columnar query engine for the HDB resale price dataset (259,237 rows, 10 columns), answering 568 $(x,y)$ pairs that each seek the minimum price-per-sqm satisfying year, month-window, town, and floor-area constraints.
Result reuse (C1+C2) reduces 568 independent $O(N)$ scans to a single build pass plus $O(1)$ lookups (486$\times$ query speedup; 738$\times$ when composed with dictionary encoding).
Pre-sorted binary search (A2+B3) independently eliminates all town comparisons (207$\times$).
With columnar file I/O (A9), the full system achieves 104.8\,ms total (45.6$\times$ end-to-end speedup) at 5.3\,MB versus 71.4\,MB baseline.

\subsection{System Architecture}\label{sec:arch}

  \caption{Pipeline: CSV~$\rightarrow$~parser~$\rightarrow$~per-column binary files~$\rightarrow$~engine~$\rightarrow$~output CSV.}

The parser dynamically detects column positions from the CSV header (supporting both the 10-column and 11-column variants of the dataset) and streams rows into parallel \texttt{std::vector} columns.
The \texttt{YYYY-MM} date string is split into \texttt{Year} (\texttt{uint16}) and \texttt{Month} (\texttt{uint8}) at parse time.
Rows with malformed dates, empty mandatory fields, or unexpected column counts are skipped with a warning.
Year-2025 rows are loaded but never matched as a target year by any valid query.

\subsection{Baseline Column Store}\label{sec:baseline-store}

The \texttt{ColumnStore} struct holds one \texttt{std::vector} per column.
Numeric columns use fixed-width types (\texttt{uint16\_t} for Year, Floor\_Area, Lease\_Commence\_Date; \texttt{uint8\_t} for Month; \texttt{uint32\_t} for Resale\_Price); string columns (Town, Block, Street\_Name, Flat\_Type, Flat\_Model, Storey\_Range) use \texttt{std::vector<std::string>}.
All columns are populated in a single sequential pass through the CSV.
The baseline loads all 10 columns into memory for a total footprint of 71.4\,MB, dominated by the six string columns (\texttt{Street\_Name} alone has 577 unique values with heap-allocated character data per row).

\subsection{Encoding and Layout Decisions}\label{sec:layout-discussion}

\paragraph{Dictionary encoding (A1).}
A \texttt{DictionaryEncoder} (bidirectional \texttt{unordered\_map}/\texttt{vector} pair) maps each of 26 unique town strings to a \texttt{uint16\_t} ID.
At query time, the engine pre-resolves the target town list to IDs once outside the scan loop, then uses integer equality in the inner loop.
Measured: 34\% query speedup (2,211$\to$1,458\,ms) at the cost of +2.9\% memory and 16\% slower load time for dictionary construction---a one-time penalty amortised across 568 queries.

\paragraph{Column splitting of \texttt{Month}.}
Splitting the date string into two integer columns at parse time eliminates repeated string parsing and enables direct \texttt{uint16} range predicates.
The Year predicate alone eliminates ${\sim}90\%$ of rows with a single integer comparison, and independent zone-map pruning on both fields becomes possible (\S\ref{sec:zonemaps}).

\paragraph{Precomputed PricePerSqm (A4).}
Storing \texttt{price / area} as \texttt{float32} eliminates a per-row floating-point division for filter survivors.
However, only ${\sim}0.2\%$ of row iterations reach this division (${\sim}543$ survivors per query), so the measured speedup is $<$0.1\%.
The column is retained because the query's aggregate target \emph{is} price-per-sqm, but the benefit is workload-dependent: it pays off only when survival rate is high.

\paragraph{Pre-sorted clustering (A2).}
A \texttt{stable\_sort} by composite key (Town, Year, Month) physically reorders all columns once at ingest using a shared permutation vector to guarantee row alignment.
A linear post-sort pass records each of the 26 town partitions' \texttt{[begin, end)} boundaries in \texttt{TownPartition} structs for $O(1)$ lookup at query time.
This $O(N \log N)$ decision (+16.7\% load overhead) is the foundation for binary search (\S\ref{sec:binsearch}) and temporally homogeneous zone-map chunks (\S\ref{sec:zonemaps}).
With A9 columnar files, the sort cost is paid once during the offline conversion step.

\paragraph{Separate binary column files (A9).}
Each column is written to its own binary file during CSV-to-columnar conversion.
At query time only the five filter columns are loaded; output columns are lazy-loaded only for the single surviving row per $(x,y)$ pair.
Memory drops from 71.4\,MB to 2.7\,MB (96.2\% reduction) and load time from 2,564\,ms to 84\,ms (96.7\% faster).
Note that A9 alone does \emph{not} improve query time---it is 2.1\% \emph{slower} (2,258\,ms vs.\ 2,211\,ms baseline) because the binary I/O path still performs a full scan, and the overhead of opening and reading separate files slightly exceeds the baseline's in-memory access pattern. A9's value is in memory and load-time reduction, which becomes significant when composed with scan-elimination techniques.

\subsection{Zone Maps (B1)}\label{sec:zonemaps}
Each numeric filter column is divided into fixed-size chunks of 1,024 rows, and a per-chunk \texttt{(min, max)} entry is stored at ingest---254 chunks totalling $<$8\,KB.
The chunk size of 1,024 was chosen to balance pruning granularity against metadata overhead: smaller chunks (e.g.\ 256) would increase metadata 4$\times$ for marginal gain, while larger chunks (e.g.\ 4,096) reduce the probability that a chunk falls entirely outside the query window.
With sorted data (A2), temporal locality maximises chunk homogeneity, achieving a 96.1\% skip rate across all 568 queries (138.6K of 144.3K chunks skipped).

\subsection{Chunked I/O (D1)}\label{sec:io}
To address the ``larger than memory'' requirement (clarification Q4), the system streams filter columns from A9 binary files in bounded-size chunks under a configurable memory budget.
The outer loop iterates over I/O chunks while the inner loop runs all 568 queries per chunk (loop inversion), exploiting the associativity of \texttt{min} to merge per-chunk winners.
Performance is detailed in \S\ref{sec:sensitivity}.

\subsection{Exception Handling}\label{sec:except}
Empty result sets produce a ``No result'' row in the output CSV.
Ties in minimum price-per-sqm are resolved by first-encountered order (clarification Q5: no penalty).

% ===================== SECTION 2: DATA PROCESSING =====================
\section{Data Processing}\label{sec:processing}

\subsection{Baseline Algorithm}\label{sec:baseline}
\begin{algorithm}[H]\footnotesize
\caption{Naive full column scan (control group).}\label{alg:baseline}
\begin{algorithmic}[1]
  \For{each $(x,y)$ in 568 query pairs}
    \State $\textit{min\_ppsm} \gets +\infty$;\; $\textit{best} \gets \textsc{None}$
    \For{$i \gets 0$ \textbf{to} $N{-}1$} \Comment{$N = 259{,}237$}
      \If{$\text{Year}[i] \neq \textit{target\_year}$} \textbf{continue} \EndIf
      \If{$\text{Month}[i] \notin [\textit{start},\,\textit{start}{+}x{-}1]$} \textbf{continue} \EndIf
      \If{$\text{Town}[i] \notin \textit{town\_list}$} \textbf{continue} \EndIf
      \If{$\text{Area}[i] < y$} \textbf{continue} \EndIf
      \State $\textit{ppsm} \gets \text{Price}[i]\;/\;\text{Area}[i]$
      \If{$\textit{ppsm} < \textit{min\_ppsm}$} update $\textit{min\_ppsm}$, $\textit{best}$ \EndIf
    \EndFor
    \State emit $\textit{best}$ (or ``No result'') to output CSV
  \EndFor
\end{algorithmic}
\end{algorithm}

The baseline iterates 568 $(x,y)$ pairs, scanning all 259,237 rows for each.
In the implementation, \texttt{runQuery} in \texttt{query\_engine.cpp} receives the \texttt{ColumnStore} reference and accesses columns by index: \texttt{db.col\_month\_year[i]}, \texttt{db.col\_month\_month[i]}, \texttt{db.col\_town[i]} (string comparison via linear scan over the 7--10 element target town list), \texttt{db.col\_floor\_area[i]}, and \texttt{db.col\_resale\_price[i]}.
Predicates are evaluated in the order Year~$\to$~Month~$\to$~Town~$\to$~Area.
Year is checked first because it is a single \texttt{uint16} equality (${\sim}1$\,ns) that eliminates ${\sim}90\%$ of rows before the more expensive Town iteration runs.
The end-of-month range is capped at 12 (\texttt{std::min(start\_month + x - 1, 12)}) to prevent queries from spanning into the next year.
Across the full grid this produces 147.25M row iterations and 12.55M town comparisons, averaging 4,774.7\,ms total (2,563.7\,ms load + 2,210.9\,ms query).

\subsection{Composable Scan Architecture}\label{sec:compose}

All 11 optimisations are controlled by independent boolean flags in the \texttt{ColumnStore} struct (toggled via \texttt{OptConfig} in the evaluation suite).
The query engine has exactly two paths: (1)~a \emph{reuse path} that short-circuits via the cumulative table (\S\ref{sec:reuse}), and (2)~a \emph{unified scan loop} where each flag controls one orthogonal decision---A1 selects int vs.\ string comparison, B1 wraps the loop in chunk-level pruning, C4 reorders predicates, C6 gates float computation, A4 selects the PPSM source, and C3 defers the price column to a Phase~2 survivors pass.
This composability is what allows the evaluation suite to test ${\sim}30$ configurations and isolate each contribution.

\subsection{Result Reuse (C1+C2)}\label{sec:reuse}

The 568 queries overlap: for fixed $y$, the month window for $x{=}k$ is a superset of $x{=}k{-}1$; for fixed $x$, every record with $\texttt{area} \ge y$ also satisfies $\texttt{area} \ge y{-}1$.

\paragraph{Three-step cumulative table build.}
\textbf{Step~1 (single $O(N)$ scan):} For each row passing year and town filters, compute $\textit{offset} = \texttt{month} - \textit{start} + 1$ (range 1--8) and $\textit{bucket} = \min(\texttt{area},\, 150)$.
Records with $\texttt{area} > 150$ are \emph{clamped} to bucket 150, not dropped---this is correct because every valid $y$ threshold is $\le 150$, so a record with area 160 satisfies every $y$ and must contribute to all buckets it qualifies for; the clamped bucket~150 propagates into all lower buckets during the Y-sweep (Step~3).
For each $(\textit{offset}, \textit{bucket})$ cell, track the minimum PricePerSqm and its row index.
\textbf{Step~2 (X-sweep):} For each area bucket, sweep offsets $1 \to 8$, propagating a running minimum.
\textbf{Step~3 (Y-sweep):} For each offset, sweep area $149 \to 80$, propagating the minimum downward.
After Step~3, \texttt{cum\_table[x][y]} holds the answer for each $(x,y)$ pair, and the query phase becomes a single array lookup.

\paragraph{Results.}
C1+C2 alone reduces query time from 2,210.9\,ms to 4.5\,ms (486$\times$ query speedup), with rows scanned dropping from 147.25M to 259.2K (the single build scan).
When composed with dictionary encoding (A1+C1+C2), the town filter inside \texttt{buildCumulativeTable} runs faster, yielding 3.0\,ms query time (738$\times$).

\subsection{Pre-sort + Binary Search (A2+B3)}\label{sec:binsearch}

With data pre-sorted by (Town, Year, Month), the query engine computes a linearised month key ($\texttt{year} \times 12 + \texttt{month} - 1$) and runs custom \texttt{lowerBound}/\texttt{upperBound} searches within each town partition to locate the exact row range---no per-row town or month comparisons.
Rows scanned drop from 147.25M to 751.7K (99.5\% reduction), town comparisons fall to zero, and query time drops to 10.7\,ms (207$\times$ query speedup).
This is an independent scan-elimination path from C1+C2: binary search narrows per-query, while reuse precomputes all 568 answers.
Without A2, B3 safely falls through to the baseline scan (verified by a B3-only config: 0.0\% change).

\subsection{Late Materialisation (C3)}\label{sec:c3}

Phase~1 applies only the four predicate columns (Year, Month, Town, Floor\_Area), appending survivor indices to a vector.
Phase~2 iterates survivors to fetch Resale\_Price, compute PricePerSqm, and track the minimum.
Measured result: 1.2\% \emph{slowdown} (2,237\,ms vs.\ 2,211\,ms), because the overhead of maintaining the survivor vector exceeds cache savings from deferring a single 4-byte column.
This technique benefits wide tables (as in Vertica and ClickHouse); our narrow schema is too small for measurable improvement.

\subsection{Other Scan Optimisations}\label{sec:other}

\paragraph{Zone-map chunk skipping (B1).}
Before scanning a 1,024-row chunk, the engine tests its min/max against Year, Month, and Floor\_Area predicates; failing chunks are skipped entirely (96.1\% skip rate, 23.5\% standalone query speedup; 57.5\% with A1).

\paragraph{Predicate reordering (C4).}
Reordering to Town~$\to$~Year~$\to$~Month~$\to$~Area caused a 1,567\% regression (0.06$\times$): town comparisons surged from 12.55M to 417.51M because every row now pays the expensive Town list iteration before the cheap Year check can eliminate it. The lesson: optimal order must minimise \emph{cost~$\times$~pass\_rate}, not maximise selectivity alone.

\paragraph{Integer early-exit gate (C6).}
Tests $\texttt{price} \times \texttt{cur\_min\_area} \ge \texttt{cur\_min\_price} \times \texttt{area}$ in \texttt{uint64} before computing float PricePerSqm.
Measured: 0.0\% speedup---too few survivors (${\sim}543$/query) for the eliminated float work to register.

\subsection{Correctness Argument}\label{sec:correctness}

Each optimisation preserves output equivalence:
\textbf{A1}~dictionary encoding is a bijection.
\textbf{A2}~sorting is a permutation.
\textbf{A4}~precomputed PPSM is identical to runtime division.
\textbf{A9}~binary files reproduce identical column vectors.
\textbf{B1}~zone maps skip a chunk only when its (min, max) proves no row can match---conservative by construction.
\textbf{B3}~binary search locates exact boundaries in sorted data.
\textbf{C1+C2}~result reuse is exact because $\min$ is associative over disjoint month ranges and monotone over area thresholds; clamping area $> 150$ to bucket~150 is correct because all valid $y \le 150$, so clamped records contribute to every bucket they qualify for and the Y-sweep propagates them downward.
\textbf{C3}~defers column access without altering the predicate set.
\textbf{C4}~changes evaluation order, not the predicates.
\textbf{C6}~is a sufficient condition for ``cannot beat current minimum.''
\textbf{D1}~processes the same rows in bounded batches; the cumulative table is merged across chunks via the associativity of $\min$.
All ${\sim}30$ configurations produced byte-identical output, verified by the evaluation suite's per-result hash comparison (\S\ref{sec:correct-inv}).

\subsection{Environment}\label{sec:env}
All benchmarks were run on an Apple M-series MacBook Air, compiled with \texttt{clang++ -O2 -std=c++17}.

% ===================== CONCLUSION =====================
\section{Conclusion}\label{sec:conclusion}
The largest win was result reuse (C1+C2): a single $O(N)$ build pass replaced $568 \times O(N)$ scans with $O(1)$ lookups (486$\times$ query speedup; 738$\times$ with A1).
Pre-sorted binary search (A2+B3) independently achieved 207$\times$ by eliminating town comparisons via partition-aware indexed access.
The most instructive failure was C4 predicate reordering (0.06$\times$), which demonstrated that optimal predicate order must minimise cost\,$\times$\,pass\_rate rather than maximise selectivity---the cheap Year check eliminates 90\% of rows before the expensive Town iteration.
If revisiting this project, we would explore a cost-based predicate optimiser that dynamically selects evaluation order based on estimated cost\,$\times$\,selectivity per column.
