% ===================== ABSTRACT =====================
\noindent\textbf{Abstract.}~%
We present our highly performant columnar store query engine.
It implements \textbf{14 distinct optimisations}, spanning five architectural layers.
They include encoding (Dictionary, Precomputed aggregates), Physical layout (Pre-sorted clustering, Per-column binary files, Town partitioning), Indexing (Zone maps, Bitmap indices, Binary search), Scan-path rewriting (Result reuse, Late materialisation, Predicate reordering, Integer gating), and I/O management (Chunked streaming, Memory-mapped I/O).
All optimisations are toggleable by boolean flags.
This enables us to build a combinatorial evaluation suite testing across 40 permutations of optimisations, each with correctness verification.
Physical town partitioning together with Result reuse achieves a \textbf{2,013$\times$ query speedup} at only 660\,KB memory.
Memory-mapped I/O with Result Reuse has the fastest end to end time of \textbf{84.8\,ms}, 58.5$\times$ faster than baseline.
Negative results are instructive as well.
Bitmap indexing ($0.08\times$) and Predicate reordering ($0.03\times$) show that remove cheap predicates via an expensive process greatly affects performance, especially when data is already well filtered upstream.

\subsection{Encoding and Layout Decisions}\label{sec:layout-discussion}

\paragraph{Dictionary encoding (A1).}
A \texttt{DictionaryEncoder} (bidirectional \texttt{unordered\_map}/\texttt{vector} pair) maps each of 26 unique town strings to a \texttt{uint16\_t} ID.
At query time, the engine pre-resolves the target town list to IDs once outside the scan loop, then uses integer equality in the inner loop.
Measured: 34\% query speedup (2,405$\to$1,585\,ms) at the cost of +2.9\% memory and 15.5\% slower load time for dictionary construction---a one-time penalty amortised across 568 queries.

\paragraph{Column splitting of \texttt{Month}.}
Splitting the date string into two integer columns at parse time eliminates repeated string parsing and enables direct \texttt{uint16} range predicates.
The Year predicate alone eliminates ${\sim}90\%$ of rows with a single integer comparison.

\paragraph{Precomputed PricePerSqm (A4).}
Storing \texttt{price / area} as \texttt{float32} eliminates a per-row floating-point division for filter survivors.
However, only ${\sim}0.2\%$ of row iterations reach this division (${\sim}543$ survivors per query), so the measured speedup is $<$0.1\%.
The column is retained because the query's aggregate target \emph{is} price-per-sqm, but the benefit is workload-dependent.

\paragraph{Pre-sorted clustering (A2).}
A \texttt{stable\_sort} by composite key (Town, Year, Month) physically reorders all columns once at ingest using a shared permutation vector.
A linear post-sort pass records each town partition's \texttt{[begin, end)} boundaries for $O(1)$ lookup at query time.
This is the foundation for binary search (\S\ref{sec:binsearch}) and temporally homogeneous zone-map chunks (\S\ref{sec:zonemaps}).

\paragraph{Separate binary column files (A9).}
Each column is written to its own binary file during CSV-to-columnar conversion.
At query time only the five filter columns are loaded; output columns are lazy-loaded only for the single surviving row per $(x,y)$ pair.
Memory drops from 71.4\,MB to 2.7\,MB (96.2\% reduction) and load time from 2,553\,ms to 114\,ms.
A9 alone does \emph{not} improve query time --- it is 2.1\% \emph{slower} because the binary I/O path still performs a full scan. A9's value is in memory and load-time reduction when composed with scan-elimination techniques.

\subsection{Zone Maps (B1)}\label{sec:zonemaps}
Each numeric filter column is divided into fixed-size chunks of 1,024 rows, and a per-chunk \texttt{(min, max)} entry is stored at ingest---254 chunks totalling $<$8\,KB.
With sorted data (A2), temporal locality maximises chunk homogeneity, achieving a 96.1\% skip rate across all 568 queries (138.6K of 144.3K chunks skipped).

\subsection{Bitmap Index on Town (B2)}\label{sec:bitmap}
One \texttt{std::vector<bool>} is built per distinct town at load time (26 bit-vectors $\times$ 259K bits $\approx$ 842\,KB).
Before the query loop, the bit-vectors for the target towns are OR-combined into a single \texttt{uint8\_t}-per-row mask ($\sim$259\,KB), replacing the per-row town predicate with a single array lookup: \texttt{if (!mask[i]) continue}.
The mask uses one byte per row instead of packed bits for cache-line-friendly sequential access in the scan loop.
Benchmark results (\S\ref{sec:negative}) show this is a \emph{negative} optimisation: eliminating all 12.55M town comparisons yielded $0.08\times$ because the per-row byte-load-and-branch adds overhead that exceeds the original integer comparison cost---the cheap Year check already prunes ${\sim}90\%$ of rows before Town is reached.

\subsection{I/O Layer: Chunked (D1) and Memory-Mapped (D2)}\label{sec:io}

\paragraph{Chunked I/O (D1).}
To address the ``larger than memory'' requirement (clarification Q4), the system streams filter columns from A9 binary files in bounded-size chunks under a configurable memory budget.
The outer loop iterates over I/O chunks while the inner loop runs all 568 queries per chunk (loop inversion), exploiting the associativity of \texttt{min} to merge per-chunk winners.

\paragraph{Memory-mapped I/O (D2).}
D2 replaces \texttt{ifstream}/\texttt{fread} with POSIX \texttt{mmap(2)}: each \texttt{.col} file is mapped into virtual address space with a single syscall, then \texttt{memcpy}'d into the existing column vectors.
This is a \emph{memcpy-from-mapped-region} approach---not true zero-copy---chosen for full compatibility with downstream optimisations.
Load time drops from 114\,ms (A9 \texttt{ifstream}) to 63\,ms (45\% reduction).
For lazy materialisation, \texttt{loadStringAtMmap} replaces \texttt{std::ifstream} construction with raw POSIX calls, avoiding C++ iostream overhead on the per-winning-row path.
D2 conflicts with D1 (opposite I/O philosophies: demand-paged vs.\ explicitly bounded) and is disabled if both are set.
Composed with reuse, D2+C1C2 achieves the fastest total time of \textbf{84.8\,ms} (58.5$\times$ end-to-end).

\subsection{Physical Partitioning by Town (E1)}\label{sec:partition}
E1 splits columnar binary files into one subdirectory per town (Hive-style partition pruning).
At query time, \texttt{loadColumnFilesPartitioned} opens only the subdirectories for the target towns and concatenates their columns into the in-memory \texttt{ColumnStore}:

\begin{lstlisting}[caption={E1 partition loading (simplified).}]
void loadColumnFilesPartitioned(const string& base_dir,
        const vector<string>& target_towns, ColumnStore& db) {
    for (const auto& town : target_towns) {
        string dir = base_dir + "/" + town;
        // append filter + materialisation columns from dir
        appendNumericCol(db.col_month_year, dir+"/month_year.col");
        appendNumericCol(db.col_floor_area, dir+"/floor_area.col");
        // ... remaining columns ...
    }
    // rebuild zone maps / bitmap indices over concatenated data
}
\end{lstlisting}

For 3 target towns, only 42,935 of 259,237 rows are loaded---an 83.4\% reduction.
The Town predicate becomes implicit: if a row is in memory, it belongs to a target town; zero town comparisons occur at scan time.
Materialisation columns are loaded eagerly (not lazy), trading higher memory for eliminating per-query file I/O.
Memory footprint drops to \textbf{660\,KB} (99.1\% less than baseline) because only target-town rows are resident.

\textit{Planned extension:} Run-length encoding (RLE) on the sorted Town column within each partition, exploiting contiguous runs created by A2 to compress \texttt{town\_encoded.col} to a single (value, count) pair per partition.

\subsection{Exception Handling}\label{sec:except}
Empty result sets produce a ``No result'' row in the output CSV.
Ties in minimum price-per-sqm are resolved by first-encountered order (clarification Q5: no penalty).

% ===================== SECTION 2: DATA PROCESSING =====================
\section{Data Processing}\label{sec:processing}

\subsection{Baseline Scan}\label{sec:baseline}
The baseline scans all 259,237 rows for each of 568 $(x,y)$ pairs.
Predicates are evaluated in the order Year~$\to$~Month~$\to$~Town~$\to$~Area; Year is checked first because it eliminates ${\sim}90\%$ of rows with a single \texttt{uint16} equality before the more expensive Town iteration runs.

\begin{lstlisting}[caption={Baseline scan loop in \texttt{runQuery} (simplified).}]
for (size_t i = 0; i < N; ++i) {
    if (db.col_month_year[i] != target_year) continue;  // ~90% eliminated
    if (db.col_month_month[i] < start_month ||
        db.col_month_month[i] > end_month)  continue;
    // Town: linear scan over 7-element target list
    bool match = false;
    for (const auto& t : towns)
        if (db.col_town[i] == t) { match = true; break; }
    if (!match) continue;
    if (db.col_floor_area[i] < y) continue;
    double ppsm = (double)db.col_resale_price[i] / db.col_floor_area[i];
    if (ppsm < min_ppsm) { min_ppsm = ppsm; best_i = i; }
}
\end{lstlisting}

Across the full grid this produces 147.25M row iterations and 12.55M town comparisons, averaging 4,957.7\,ms total (2,552.9\,ms load + 2,404.8\,ms query).

\subsection{Composable Scan Architecture}\label{sec:compose}

All 14 optimisations are controlled by independent boolean flags in the \texttt{ColumnStore} struct (toggled via \texttt{OptConfig} in the evaluation suite).
The query engine has three paths: (1)~a \emph{reuse path} (C1+C2) that short-circuits via the cumulative table (\S\ref{sec:reuse}), (2)~a \emph{unified scan loop} where each flag controls one orthogonal decision---A1 selects int vs.\ string comparison, B1 wraps the loop in chunk-level pruning, B2 replaces the town predicate with a bitmap mask, C4 reorders predicates, C6 gates float computation, A4 selects the PPSM source, and C3 defers the price column to a Phase~2 survivors pass, and (3)~a \emph{partition-pruned path} (E1) that loads only target-town data before entering either path~(1) or~(2).
D2 (mmap) is an I/O-layer substitution under A9, transparent to the scan logic.
This composability allows the evaluation suite to test ${\sim}40$ configurations and isolate each contribution.

\subsection{Result Reuse (C1+C2)}\label{sec:reuse}

The 568 queries overlap: for fixed $y$, the month window for $x{=}k$ is a superset of $x{=}k{-}1$; for fixed $x$, every record with $\texttt{area} \ge y$ also satisfies $\texttt{area} \ge y{-}1$.

\paragraph{Three-step cumulative table build.}
\textbf{Step~1 (single $O(N)$ scan):} For each row passing year and town filters, compute $\textit{offset} = \texttt{month} - \textit{start} + 1$ (range 1--8) and $\textit{bucket} = \min(\texttt{area},\, 150)$.
Records with $\texttt{area} > 150$ are \emph{clamped} to bucket 150, not dropped---this is correct because every valid $y$ threshold is $\le 150$, so a record with area 160 satisfies every $y$ and must contribute to all buckets it qualifies for; the clamped bucket propagates into all lower buckets during the Y-sweep.

\begin{lstlisting}[caption={\texttt{buildCumulativeTable} — Step 1 scan (core loop).}]
vector<vector<MinEntry>> per_x(9, vector<MinEntry>(151));
for (size_t i = 0; i < N; ++i) {
    if (db.col_month_year[i] != target_year) continue;
    uint8_t month = db.col_month_month[i];
    if (month < start_month) continue;
    int offset = (int)month - (int)start_month + 1;
    if (offset < 1 || offset > 8) continue;
    // town filter (A1-aware: int vs string)
    if (db.use_dict_encoding) {
        bool match = false;
        for (auto& tid : town_ids)
            if (db.col_town_encoded[i] == tid) { match = true; break; }
        if (!match) continue;
    } else { if (town_set.find(db.col_town[i]) == town_set.end()) continue; }
    unsigned area = db.col_floor_area[i];
    if (area < 80) continue;
    unsigned bucket = (area > 150) ? 150u : area;  // clamp, NOT drop
    double ppsm = (double)db.col_resale_price[i] / db.col_floor_area[i];
    if (!per_x[offset][bucket].has || ppsm < per_x[offset][bucket].ppsm)
        per_x[offset][bucket] = {true, ppsm, i};
}
\end{lstlisting}

\textbf{Step~2 (X-sweep):} For each area bucket, sweep offsets $1 \to 8$, propagating a running minimum.
\textbf{Step~3 (Y-sweep):} For each offset, sweep area $149 \to 80$, propagating the minimum downward.
After Step~3, \texttt{cum\_table[x][y]} holds the answer for each $(x,y)$ pair, and the query phase becomes a single array lookup.

\paragraph{Results.}
C1+C2 alone reduces query time from 2,404.8\,ms to 4.6\,ms (528$\times$ query speedup), with rows scanned dropping from 147.25M to 259.2K (the single build scan).
When composed with dictionary encoding (A1+C1+C2), query time drops to 3.3\,ms (721$\times$).

\subsection{Pre-sort + Binary Search (A2+B3)}\label{sec:binsearch}

With data pre-sorted by (Town, Year, Month), the query engine runs custom \texttt{lowerBound}/\texttt{upperBound} searches within each town partition using a linearised month key ($\texttt{year} \times 12 + \texttt{month} - 1$):

\begin{lstlisting}[caption={Binary search on linearised month key.}]
inline uint32_t monthKey(uint16_t year, uint8_t month) {
    return (uint32_t)year * 12u + (uint32_t)(month - 1u);
}
size_t lowerBoundMonthKey(const ColumnStore& db, size_t l, size_t r,
                          uint32_t key) {
    while (l < r) {
        size_t mid = l + (r - l) / 2;
        if (monthKeyAt(db, mid) < key) l = mid + 1; else r = mid;
    }
    return l;
}
\end{lstlisting}

Rows scanned drop from 147.25M to 751.7K (99.5\% reduction), town comparisons fall to zero, and query time drops to 16.3\,ms (148$\times$ query speedup).
This is an independent scan-elimination path from C1+C2.

\subsection{Late Materialisation (C3)}\label{sec:c3}

Phase~1 applies only the four predicate columns, appending survivor indices to a vector.
Phase~2 iterates survivors to fetch Resale\_Price, compute PricePerSqm, and track the minimum.
Measured result: 103\% \emph{slowdown} (4,888\,ms vs.\ 2,405\,ms), because the overhead of maintaining the survivor vector exceeds cache savings from deferring a single 4-byte column.

\subsection{Other Scan Optimisations}\label{sec:other}

\paragraph{Zone-map chunk skipping (B1).}
Before scanning a 1,024-row chunk, the engine tests its min/max against Year, Month, and Floor\_Area predicates; failing chunks are skipped entirely (96.1\% skip rate, 21\% standalone query speedup; combined with A1: 20.8\%).

\paragraph{Bitmap-driven row filtering (B2).}
A precomputed \texttt{uint8\_t} mask replaces the per-row town loop with a single byte lookup.
Town comparisons drop to zero, but query time regressed to $0.08\times$ ($31{,}782$\,ms vs.\ $2{,}405$\,ms baseline): the byte-load-plus-branch on every row is more expensive than the original integer comparison that runs only on the ${\sim}10\%$ of rows surviving the Year filter.
This confirms that the baseline Year$\to$Month$\to$Town order is already near-optimal.

\paragraph{Predicate reordering (C4).}
Reordering to Town~$\to$~Year~$\to$~Month~$\to$~Area caused a $0.03\times$ regression: town comparisons surged from 12.55M to 417.51M because every row now pays the expensive Town list iteration before the cheap Year check can eliminate it. The lesson: optimal order must minimise \emph{cost~$\times$~pass\_rate}, not maximise selectivity alone.

\paragraph{Integer early-exit gate (C6).}
Tests $\texttt{price} \times \texttt{cur\_min\_area} \ge \texttt{cur\_min\_price} \times \texttt{area}$ in \texttt{uint64} before computing float PricePerSqm.
Measured: within noise---too few survivors (${\sim}543$/query) for the eliminated float work to register.

\subsection{Correctness Argument}\label{sec:correctness}

Each optimisation preserves output equivalence:
\textbf{A1}~dictionary encoding is a bijection.
\textbf{A2}~sorting is a permutation.
\textbf{A4}~precomputed PPSM is identical to runtime division.
\textbf{A9}~binary files reproduce identical column vectors.
\textbf{B1}~zone maps skip a chunk only when its (min, max) proves no row can match.
\textbf{B2}~bitmap mask is the OR of exact per-town bit-vectors; the mask lookup is equivalent to the membership test it replaces.
\textbf{B3}~binary search locates exact boundaries in sorted data.
\textbf{C1+C2}~result reuse is exact because $\min$ is associative over disjoint month ranges and monotone over area thresholds; clamping area $> 150$ to bucket~150 is correct because all valid $y \le 150$.
\textbf{C3}~defers column access without altering the predicate set.
\textbf{C4}~changes evaluation order, not the predicates.
\textbf{C6}~is a sufficient condition for ``cannot beat current minimum.''
\textbf{D1}~processes the same rows in bounded batches; the cumulative table is merged across chunks via the associativity of $\min$.
\textbf{D2}~\texttt{memcpy} from mapped region produces byte-identical vectors as \texttt{fread}.
\textbf{E1}~partition loading concatenates disjoint town subsets; the union equals the set of rows matching the town predicate.
All ${\sim}40$ configurations produced byte-identical output, verified by the evaluation suite's per-result hash comparison (\S\ref{sec:correct-inv}).

% ===================== CONCLUSION =====================
\section{Conclusion}\label{sec:conclusion}
The largest query-time win was result reuse (C1+C2): a single $O(N)$ build pass replaced $568 \times O(N)$ scans with $O(1)$ lookups (528$\times$ query speedup; 721$\times$ with A1).
Physical town partitioning (E1) reduced the build-pass input from 259.2K to 42.9K rows, yielding 2{,}013$\times$ query speedup and 660\,KB memory---the most memory-efficient configuration.
The fastest end-to-end configuration was D2+C1C2 (mmap + reuse) at 84.8\,ms total (58.5$\times$), where mmap's 45\% load-time reduction composed with reuse's scan elimination.
The most instructive failures were C4 predicate reordering ($0.03\times$) and B2 bitmap indexing ($0.08\times$): C4 demonstrated that optimal predicate order must minimise cost\,$\times$\,pass\_rate, while B2 showed that eliminating a cheap predicate via a more expensive mechanism can regress performance when upstream predicates already prune effectively.
Across all 14 optimisations and ${\sim}40$ tested configurations, every result was byte-identical to the baseline---correctness was never sacrificed for speed.
If revisiting this project, we would explore RLE compression on sorted partition columns and a cost-based predicate optimiser that dynamically selects evaluation order.
