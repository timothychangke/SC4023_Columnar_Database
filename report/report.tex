\subsection{System Architecture}\label{sec:arch}
\begin{figure}[H]\centering
  % \includegraphics[width=0.85\linewidth]{figs/architecture.pdf}
  \caption{Pipeline: CSV~$\rightarrow$~parser~$\rightarrow$~per-column binary files~$\rightarrow$~engine~$\rightarrow$~output CSV.}
  \label{fig:arch}
\end{figure}
Figure~\ref{fig:arch} shows the end-to-end pipeline.
The parser splits the CSV \texttt{YYYY-MM} field into two integer columns (\texttt{Year} as \texttt{uint16}, \texttt{Month} as \texttt{uint8}), precomputes \texttt{PricePerSqm} (A4), and drops columns unused by the query (\texttt{Storey\_Range}, \texttt{Street\_Name}, \texttt{Flat\_Type}) so that neither the binary files nor the scan loop pay for data the workload never touches.

\subsection{Per-Column Physical Layout}\label{sec:layout}
Table~\ref{tab:layout} details each materialised column.
The six columns on the scan hot path (Year through PricePerSqm) total 14~bytes/row; because only these columns are read during filtering and aggregation, the effective working set for 259K rows is $\approx$3.5\,MB---comfortably L3-resident.
Late-materialised columns (Block, Flat\_Model, Lease\_Commence) are fetched only for the single surviving output row per $(x,y)$ pair (\S\ref{sec:c3}).

\subsection{Encoding and Layout Decisions}\label{sec:layout-discussion}

\paragraph{Dictionary encoding (A1).}
A \texttt{DictionaryEncoder} maps each unique town string to a \texttt{uint16\_t} ID via a bidirectional hash-map/vector pair, converting ${\sim}20$\,ns string comparisons into ${\sim}1$\,ns integer equality checks.
With only 26 unique towns in the dataset (10 per query), the dictionary occupies $<$1\,KB---negligible overhead---while the encoded column adds 2\,bytes/row.
The cost is an extra hash-map insert per row at load time (${\sim}0.2\%$ slower ingest), but every downstream scan benefits: measured $+16.6\%$ query speedup from this change alone.

\paragraph{Column splitting of \texttt{Month}.}
The source CSV stores dates as strings (e.g.\ \texttt{"Jan-15"}); the parser converts each into \texttt{Year} (\texttt{uint16}) and \texttt{Month} (\texttt{uint8}) at ingest time, paying a one-time parse cost to enable direct integer range predicates and avoid ${\sim}147$M repeated string parses across all 568 queries.
The 3-byte pair also enables zone-map pruning on both fields independently (\S\ref{sec:zonemaps}).

\paragraph{Precomputed \texttt{PricePerSqm} (A4).}
Storing \texttt{price\,/\,area} as a \texttt{float32} column costs $+4$\,bytes/row (${\approx}1$\,MB for 259K rows) but eliminates a floating-point division for every row that survives all four filter predicates.
In practice the measured speedup is $<0.1\%$ because only ${\sim}0.2\%$ of row iterations reach the division; however, the column is retained because the query's aggregate target \emph{is} price-per-sqm---in a workload that did not aggregate on this metric, the extra storage would be wasted.

\paragraph{Sorted clustering by $(\text{Year},\text{Month},\text{Town})$.}
All columns are co-sorted by (Year, Month, Town) once at ingest---an $O(N \log N)$ cost amortised across all 568 queries.
This single decision is the foundation for three other optimisations: zone-map chunk pruning achieves a 96.1\% skip rate because temporal locality is maximised (\S\ref{sec:zonemaps}), binary search narrows the scan window to $O(\log N)$ (\S\ref{sec:binsearch}), and RLE on the Town column compresses consecutive identical IDs (\S\ref{sec:rle}).
The trade-off is ingest-time cost and the loss of insertion-order locality, both acceptable given a single bulk load.
